# Developer notes: Cloudflare Worker setup (admin portal, Phase 3)

Local-only setup for the admin portal. There is no Cloudflare account, no `wrangler login`, no remote resources and no
deploys. Everything below runs on your computer in workerd (Miniflare). The public site is still deployed to GitHub
Pages from `dist/client` (see "GitHub Pages" below).

Design: `admin-portal-design.md`, with `admin-portal-amendments.md` taking priority. Both files are outside the repo.

## What runs where

| Request | Served by |
|---|---|
| Prerendered pages, `/_astro/*`, images, `/build.json`, `robots.txt`, sitemap | Static assets from `dist/client`. Cloudflare serves these before the Worker, which never runs for them. Headers come from `public/_headers`. |
| `/api/*`, `/media/*`, `/admin/*`, `/_image` (admin/local hosts only), unknown paths | The Worker: `src/worker.ts` → Astro handler → `src/middleware.ts` → route |
| Cron `*/15 * * * *` | `src/worker.ts` `scheduled()` → `runDueJobs()` in `src/server/jobs.ts` (stub until the integrator wires the jobs) |

Files and what they do:

- **`astro.config.mjs`**
  - `@astrojs/cloudflare` with `imageService: 'compile'`, `session: false` and `security.checkOrigin: true`.
  - A sitemap filter for `/admin/`, `/api/` and `/media/`, `server.allowedHosts` for the real host names, and a small Vite plugin that keeps the public CSS byte-identical (see "Zero-diff gate").
  - `BEEZY_STATE_DIR` and `BEEZY_INSPECTOR_PORT` (below).
  - A Vite define `__BEEZY_BUILD_INFO__` that `/build.json` uses.
- **`wrangler.jsonc`**
  - Worker `beezyhoney`, `main: src/worker.ts`.
  - Assets: `dist/client`, binding `ASSETS`, `html_handling: force-trailing-slash`, `not_found_handling: 404-page`.
  - Bindings: D1 `DB` (`beezy`, `db/migrations`), KV `MEDIA` and `BACKUPS`, `send_email` `LOGIN_MAIL` with no address restrictions.
  - Cron `*/15 * * * *`, vars `PUBLIC_HOSTS` / `ADMIN_HOST` / `PUBLIC_ORIGIN`, `workers_dev: false`, `preview_urls: false`, observability on, and an optional `env.staging` that nothing uses.
  - All ids are placeholders.
- **`src/worker.ts`**: the custom entry. `fetch` is Astro's `handle`, plus `scheduled()`.
- **`src/middleware.ts`**: host routing, the admin gate, the unsafe-method origin check, admin headers and the lazy job trigger. Details below.
- **`src/server/auth.ts`** (STUB): `requireAdmin(context)`, `ADMIN_OPEN_PATHS`. The endpoints/auth agent replaces the body with the email-code login (A1) and keeps the names.
- **`src/server/jobs.ts`** (STUB): `runDueJobs(env, ctx, info)` and `maybeRunJobsLazily(env, ctx)`. The integrator wires the real jobs.
- **`src/pages/api/health.json.ts`**: on-demand, `{ok, service, time, checks:{db, media, backups, mail}}`, no-store. Returns 503 if a binding is missing.
- **`src/pages/build.json.ts`**: prerendered `/build.json` with `{siteVersion, liveVersion, builtAt, commit, source}`. `_headers` gives it `no-store`.
- **`src/env.d.ts`**: `App.Locals.admin` and `__BEEZY_BUILD_INFO__`. It references `worker-configuration.d.ts`, which is generated by `npm run types` (`wrangler types --env-file .dev.vars.example`, so only placeholder names are used and never your real `.dev.vars`).
- **`scripts/check-dist.mjs`**: the build gate. **`scripts/dist-baseline.json`**: its committed budget (from the Phase 0 baseline).

Toolchain (exact pins in `package.json`): `@astrojs/cloudflare 14.4.8` (peer `astro ^7.4.0`), `wrangler 4.160.0`,
`@cloudflare/vitest-plugin 1.7.0`, `vitest 5.1.0`. The versions were chosen so the whole tree uses one `miniflare 5.20261110.0-beta`
and one `workerd 1.20261110.1`, so the dev server, `wrangler d1 --local`, preview and the worker tests all read
and write the same local storage format. The adapter's `@cloudflare/vite-plugin 1.69.1` pins wrangler 4.160.0, and
`@cloudflare/vitest-plugin 1.7.0` is the newest release built on that same wrangler. Upgrade them together and check with
`npm ls wrangler miniflare workerd`.

## Local setup

1. `npm ci`.
2. `cp .dev.vars.example .dev.vars` and fill it in. `.dev.vars` is gitignored and is the only place the real owner emails may live. Its variables:
   - `DEV_ADMIN_EMAIL`
   - `ADMIN_EMAILS` (comma-separated)
   - `ADMIN_ALIASES` (optional; comma-separated `alias=target` pairs, target from `ADMIN_EMAILS`; see "Admin login" below)
   - `LOGIN_SECRET` (64 hex characters)
   - `IP_HASH_KEY` (required outside `astro dev`: without it every admin route answers 503)
   - `PUBLIC_HOSTS` (`beezyhoney.in,next.beezyhoney.in,localhost,127.0.0.1`: the local names act as public and admin host; `wrangler.jsonc` lists only the real hosts)
   - `DEPLOY_HOOK_URL` (empty means publishing is off on this computer)
3. Create and seed your local database (below).
4. `npm run dev -- --port <your port> --host 127.0.0.1`. This runs `astro dev` inside workerd through the Cloudflare Vite plugin.
   - Public pages: `http://127.0.0.1:<port>/`.
   - Admin: `http://127.0.0.1:<port>/admin/`. With the dev bypass you are signed in as `DEV_ADMIN_EMAIL` with role `owner`.

### Your own local database: `BEEZY_STATE_DIR`

Local D1, KV and cache data lives in `$BEEZY_STATE_DIR/v3/` (default `.wrangler/state/v3/`). Each person or agent can
use their own folder, so parallel runs never share or reset each other's data:

```sh
# Git Bash
export BEEZY_STATE_DIR=.wrangler/state-myname          # any folder; .wrangler/ and .beezy-state*/ are gitignored
npx wrangler d1 migrations apply beezy --local --persist-to "$BEEZY_STATE_DIR"     # apply db/migrations/*.sql
npx wrangler d1 execute beezy --local --persist-to "$BEEZY_STATE_DIR" --file db/seed.sql   # seed (when db/seed.sql exists)
npx wrangler d1 execute beezy --local --persist-to "$BEEZY_STATE_DIR" --command "SELECT count(*) FROM products"
npm run dev -- --port 4411 --host 127.0.0.1             # reads the same folder
```

```powershell
# PowerShell
$env:BEEZY_STATE_DIR = '.wrangler/state-myname'
npx wrangler d1 migrations apply beezy --local --persist-to $env:BEEZY_STATE_DIR
```

- `astro.config.mjs` passes `persistState: { path: BEEZY_STATE_DIR }` to the adapter, which hands it to the Cloudflare Vite plugin. The plugin stores data in `<dir>/v3`.
- `wrangler … --local --persist-to <dir>` also uses `<dir>/v3`. Same folder, same database. This was checked (day-one check (a)).
- The npm scripts `db:migrate:local`, `db:seed:local` and `db:reset:local` call `scripts/db-local.mjs`, which the data agent owns. That script must pass `--persist-to "${BEEZY_STATE_DIR:-.wrangler/state}"` to wrangler.
- `migrations apply` runs without a prompt in a non-interactive shell ("Using fallback value in non-interactive context: yes").
- To reset your database, stop your servers and delete your own `$BEEZY_STATE_DIR` folder. Never delete another person's folder.

### Ports and other processes

- The dev and preview servers use only the port you pass (`--port`). The workerd inspector is **off** by default so it never takes port 9229+. To debug with DevTools, set `BEEZY_INSPECTOR_PORT=<one of your ports>`.
- workerd also opens internal loopback sockets on random ephemeral ports. These cannot be configured and are not reachable from outside.
- Stop servers by PID. In PowerShell, find the PID with `Get-NetTCPConnection -LocalPort <port>`, then run `taskkill /T /F /PID <parent pid>`.

### Trying host routing locally

`localhost` and `127.0.0.1` count as public **and** admin host, because `.dev.vars` adds them to `PUBLIC_HOSTS` (the deployed
Worker never lists them; `predeploy-check` refuses a config that does). To see production behaviour, send a real host name. Those
names are in `server.allowedHosts`, so the dev and preview servers accept them:

```sh
curl -H "Host: beezyhoney.in" http://127.0.0.1:4411/admin/              # 404 (admin not on the public host)
curl -H "Host: admin.beezyhoney.in" http://127.0.0.1:4411/api/health.json   # 404 (api not on the admin host)
curl -H "Host: admin.beezyhoney.in" -H "Sec-Fetch-Mode: navigate" http://127.0.0.1:4411/admin/   # 303 to /admin/login/ (no dev bypass off localhost)
```

Any other Host is blocked by Vite itself (403 "Blocked request") before the Worker runs. The Worker's own unknown-host
404 is covered by `test/worker/build/middleware.test.ts`.

## Middleware rules (`src/middleware.ts`)

1. Prerendered routes skip the middleware.
2. **Host routing** is decided by the matched route (`context.routePattern`), so `/%61dmin/` cannot get past it:
   - public host (`PUBLIC_HOSTS`): `/api/*` and `/media/*`;
   - admin host (`ADMIN_HOST`): `/admin*` and `/_image`;
   - `localhost` / `127.0.0.1` (only when listed in `PUBLIC_HOSTS`, which only `.dev.vars` and the worker-test vars do): all of these;
   - the `/404` and `/500` error routes pass through on known hosts;
   - everything else gets a 404. The response is the site's own 404 page (fetched from `ASSETS` at `/404/`) with status 404, or plain text when that page does not exist (in dev).
3. **Unsafe methods** (anything except GET, HEAD and OPTIONS) on admin routes need `Sec-Fetch-Site: same-origin`. If that header is missing, they need an `Origin` equal to the request origin. Otherwise the answer is 403.
   - Astro's `security.checkOrigin` also covers form posts on every on-demand route. It runs **before** this middleware and answers a plain `403 Cross-site POST form submissions are forbidden` (without the admin headers) when the content type is form-like (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`) or missing, and `Sec-Fetch-Site` is `cross-site`/`same-site` or `Origin` differs (`node_modules/astro/dist/core/app/origin-check.js`).
   - The public `POST /api/orders.json` does its own checks and always answers 204 (contract 3), so the middleware does not 403 it. Note that its body is `text/plain`, so a **cross-site** order post gets Astro's 403 before the endpoint runs. Same-origin posts from the site (fetch keepalive or sendBeacon) are never affected.
4. **Admin gate**: `requireAdmin(context)` runs for every admin route except `ADMIN_OPEN_PATHS` (`/admin/login/` and `/admin/logout/`).
   - The result goes into `Astro.locals.admin = { email, role }`.
   - `src/server/auth.ts` is the A1 email-code login. Without a valid session the answer is a 303 to `/admin/login/?next=…` (pages) or 401 JSON (`/admin/api/*`). When `ADMIN_EMAILS` or `LOGIN_SECRET` is missing (or `LOGIN_SECRET` is shorter than 32 characters) every admin route answers **503** (fail closed).
   - The dev bypass signs you in only inside `if (import.meta.env.DEV)` and only on `localhost` / `127.0.0.1`, using `DEV_ADMIN_EMAIL`. Leave `DEV_ADMIN_EMAIL` empty in `.dev.vars` to try the real login in dev (the `send_email` simulation writes each mail to a local `.eml` file and logs its path).
   - A production build contains no bypass code. `check-dist` greps `dist/server` to prove it.
5. **Admin response headers**:
   - `Cache-Control: no-store`
   - `X-Robots-Tag: noindex, nofollow`
   - `X-Frame-Options: DENY`
   - `Referrer-Policy: same-origin`
   - `X-Content-Type-Options: nosniff`
   - `Content-Security-Policy: frame-ancestors 'none'; base-uri 'none'; object-src 'none'; form-action 'self'; connect-src 'self'; img-src 'self' blob: data:`. There is no `script-src`, so Astro's inline scripts keep working.

   Every other on-demand response gets `nosniff`.
6. **Lazy jobs**: a signed-in admin GET calls `maybeRunJobsLazily()`. It runs `runDueJobs()` in `waitUntil`, at most once per isolate every 5 minutes. This is the fallback if the cron is late.
7. **Paths without the trailing slash** (`/admin`, `/api`, `/foo`) get Astro's `301` to the slash form before the middleware runs, on every host, exactly like any unknown path. The slash form then gets the host rules above (for example `/admin/` on the public host → 404), so the redirect reveals nothing.
8. **Admin host root**: `admin.beezyhoney.in/` matches the static home page, which is served before the Worker runs. Production needs the zone's Single Redirect rule (hostname is `admin.beezyhoney.in` and the path does not start with `/admin` → 302 to `/admin/`), as amendment A1 says. The rule MUST skip the admin's own static files (`/_astro/*`, `/favicon.png`, `/apple-touch-icon.png`), which are also served before the Worker: a plain "not /admin" rule redirects the CSS and JS to the login page and the admin shows unstyled (seen 18 Nov 2026). Exact expression in RUNBOOK §3 step 9.

## Tests

`npm test` runs both Vitest projects (`vitest.config.mjs`):

- **unit** (`npm run test:unit`): Node, `test/unit/**`. The catalog agent's tests moved to `test/unit/catalog/`. Mine are in `test/unit/build/`.
- **worker** (`npm run test:worker`): `@cloudflare/vitest-plugin` runs `test/worker/**` inside workerd.
  - The bindings come from `wrangler.jsonc` (D1 `DB`, KV `MEDIA` and `BACKUPS`, `LOGIN_MAIL`, vars). They are local simulations.
  - Storage is isolated per test **file**.
  - `test/worker/setup.ts` applies `db/migrations/*.sql` (from `env.TEST_MIGRATIONS`) before each file.
  - The secrets are fixed test values from `WORKER_TEST_VARS` in `vitest.config.mjs`, never your `.dev.vars`. The owner emails therefore never appear in test runs.
  - The Worker under test is the real `src/worker.ts`. `@astrojs/cloudflare/handler` is aliased to `test/worker/stubs/astro-handler.ts`, because Astro's handler needs build-time virtual modules. To test a route, import its module and call `GET` / `POST` with a small context. To test middleware, call `onRequest(ctx, next)`. See `test/worker/build/*.test.ts`.
  - `import { env } from 'cloudflare:workers'` gives the bindings. `cloudflare:test` provides `createExecutionContext`, `createScheduledController`, `applyD1Migrations` and the other helpers.
  - `vi.stubEnv('DEV', false)` switches `import.meta.env.DEV` for a test.

## Build, preview and gates

- `npm run build` = `node scripts/sync-catalog.mjs && astro build && node scripts/check-dist.mjs`.
  - Output: `dist/client` holds the static site. `dist/server` holds the Worker (`entry.mjs`, `wrangler.json` and a local `.dev.vars` copy for preview).
  - `dist/` is gitignored. `dist/server/.dev.vars` is never uploaded, because wrangler deploys `entry.mjs` plus the assets, and `dist/client/.assetsignore` lists `.dev.vars` and `wrangler.json`.
- `npx astro preview --port <port> --host 127.0.0.1`, with the same `BEEZY_STATE_DIR` as your dev runs. This is the production build in workerd: no dev bypass, `/admin/` sends you to `/admin/login/`.
- **Fire the cron** in preview with `curl "http://127.0.0.1:<port>/cdn-cgi/handler/scheduled?cron=*/15+*+*+*+*"` (or `/cdn-cgi/local/scheduled?...`). The log shows `[jobs] runDueJobs trigger=cron cron=*/15 * * * *`.

### `scripts/check-dist.mjs`

It fails the build on any of these:

1. any `/_image` URL in `dist/client`;
2. a third-party resource on a visitor page:
   - `src`, `srcset`, `poster`, `data`, `action` or `style url()`;
   - a loading `<link href>` (canonical-type links are allowed);
   - `<script src>`;
   - CSS `url()` / `@import`;
   - a URL in JavaScript whose host is not on `JS_ALLOWED_HOSTS`. That list is `wa.me`, `api.whatsapp.com` and Instagram (links), `www.w3.org` (SVG namespace) and `gsap.com` (licence text);
3. any file under `dist/client/admin`, `/api` or `/media` (it would shadow the Worker route);
4. WebP count below 90% of `scripts/dist-baseline.json` (523, so the minimum is 471);
5. a page's JavaScript (gzip: the files it loads, its inline scripts, and the chunks it can `import()` on demand later) above its baseline + `JS_BUDGET_EXTRA_GZIP` (9 KB, see "Integration notes" below). New pages get the largest baseline. Per-page numbers (at load + on demand) are printed on every run;
6. production Worker code in `dist/server` containing `DEV_ADMIN_EMAIL` or `BEEZY_E2E_HOOK`. `*.map` files are skipped, because they carry the public sources. `--mode e2e` allows the e2e hook;
7. any value from the local `.dev.vars` (owner emails, keys; values are never printed) appearing anywhere in dist except `dist/server/.dev.vars`;
8. `dist/client/.dev.vars` existing.

Options: `--dist <dir>`, `--baseline <file>`, `--mode e2e`.

To rebuild the budget file from a fresh baseline:
`node scripts/dist-stats.mjs <dist> --out stats.json && node scripts/check-dist.mjs --write-baseline stats.json`.

The design's "live product page without a price slot" check is not in check-dist; the browser checks in the integration run cover it.

## Known caveats

- On Windows, a failed `astro build` sometimes ends with `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)` and exit code 127 while workerd shuts down. The real error is printed above that line.
- During a build the adapter copies `.dev.vars` into `process.env` (`loadWranglerEnv`). Never read secrets through `import.meta.env` in server code, because Vite would inline them. Read them only from `env` (`cloudflare:workers`) at request time. check-dist catches a leak.
- `worker-configuration.d.ts` is large (about 600 KB of runtime types). Regenerate it with `npm run types` after changing bindings or vars, and `npx wrangler types --env-file .dev.vars.example --check` tells you whether it is stale. TypeScript itself is not installed in the repo.

## Integration notes (16 Nov 2026)

**Schema change on 15 Nov around 22:20.** `db/migrations/0001_init.sql` changed (timestamp and tone CHECKs rewritten for D1's
50-byte LIKE/GLOB limit, new `orders.create_key`). A local D1 migrated before then must be rebuilt:
`npm run db:reset:local` (with your own `BEEZY_STATE_DIR`). D1 also refuses compound SELECTs with more than 5 terms and
more than 100 bound parameters; `test/helpers/d1-sqlite.ts` enforces the first two in unit tests.

**`assets.run_worker_first` in `wrangler.jsonc`** is `['/admin', '/admin/*', '/api/*', '/media/*']`. With
`not_found_handling: '404-page'` and a compatibility date after 2025-04-01, the asset layer answers unmatched browser
*navigations* (requests with `Sec-Fetch-Mode: navigate`) with the static 404 page and the Worker never runs. curl does not
send that header, so it hides the problem: test admin routing with `-H "Sec-Fetch-Mode: navigate"`. The list is selective,
so public pages stay free static assets.

**Admin login (A1).** Secrets `ADMIN_EMAILS` (the two owner emails, comma-separated; never in a tracked file) and
`LOGIN_SECRET` (64 hex characters = 32 random bytes). Rotating `LOGIN_SECRET` logs everyone out and voids every email code
and recovery code. Recovery codes: `/admin/login/recovery/` (linked from Help and Backup). Code: `src/server/auth.ts`,
`src/server/mail.ts`, pages in `src/pages/admin/login/**` and `src/pages/admin/logout/`.

**Login aliases.** Optional secret `ADMIN_ALIASES`: comma-separated `alias=target` pairs (trimmed, lower-cased), e.g.
`name@beezyhoney.in=<owner's Gmail>`. The owners type their `@beezyhoney.in` address (an Email Routing rule forwarding to
the Gmail); `send_email` can only deliver to verified destinations, so `resolveLoginEmail()` maps the alias to its
target at every login step (send, resend, code, recovery code). From there everything uses the target: rate-limit
buckets (shared between alias and Gmail), the code, the mail, the session, roles, audit and "removal ends sessions".
The login cookie and the page keep what was typed, so the Gmail is never shown, and an unknown alias gets the same
answer as any unknown email. Ignored pairs: malformed, alias = target, alias already in `ADMIN_EMAILS`, a repeated
alias (the first wins), and a target that is neither in `ADMIN_EMAILS` nor an active helper. Typing the Gmail still
works. People shows such an owner as the alias, with the Gmail masked (`n•••••e@gmail.com`); adding a helper with an
alias address is refused. Worker tests set `ADMIN_ALIASES` to empty (vitest.config.mjs) so a local `.dev.vars` never
leaks in; `check-dist` treats each address of the pairs as a secret that must not appear in `dist`.

**E2E builds.** `npm run build:e2e` builds with `--mode e2e`; only then does `GET /api/e2e/login-code.json?email=…` (local hosts
only) return the last login code. Never deploy an e2e build (`predeploy-check` refuses it); run `npm run build` afterwards.
To serve a build without your real `.dev.vars`, copy `dist` somewhere outside the repo, write a test-only
`server/.dev.vars` (`ADMIN_EMAILS=owner@example.test`, a random 64-hex `LOGIN_SECRET`, any `IP_HASH_KEY`,
`PUBLIC_HOSTS=beezyhoney.in,next.beezyhoney.in,localhost,127.0.0.1`, empty `DEV_ADMIN_EMAIL`) and run
`node node_modules/wrangler/bin/wrangler.js dev --config <copy>/server/wrangler.json --port <p> --ip 127.0.0.1 --persist-to <state> --inspector-port <p2>`.

**One `astro dev` per project.** Astro 7.4 locks the project: a second `astro dev` refuses to start (`--ignore-lock` allows
it; `--force` kills the other server).

**Deploy.** `npm run deploy` = `predeploy-check && wrangler deploy`; use it as the Workers Builds deploy command. Escape
hatches: `ALLOW_SNAPSHOT_DEPLOY=1` (deploy a snapshot build), `ALLOW_DOWNGRADE=1`. See `docs/RUNBOOK.md`.

**Jobs.** `src/server/jobs.ts` now calls `runDueJobsImpl()` from `src/server/jobs-impl.ts` (publish-if-due, one backup step
from 02:30 IST, daily clean-up, weekly reconcile). Fire it in preview with
`curl "http://127.0.0.1:<port>/cdn-cgi/handler/scheduled?cron=*/15+*+*+*+*"`; the log line lists what ran.

**`/api/live.json` while prices are hidden** carries no price or MRP (`null`), the same as the baked `#price-data`.

**Offer pill (v2).** `Base.astro` has a hidden `[data-offer]` pill fixed above the WhatsApp button; `site.ts` (`offerPill()`)
shows `activeOffer()` from `live.ts` (baked `#price-data` offer, then `/api/live.json`), hides it after its `until` day
(IST) and for the rest of the session once the visitor taps ×. Fixed position, so no layout shift. Pages without price
slots (and an empty order) do not fetch live data, so a new offer reaches them with the next website update.

**JS budget.** `JS_BUDGET_EXTRA_GZIP` is 9 KB, and on-demand chunks now count. Measured on 16 Nov 2026: home +6.0 KB at
load, product pages +7.1 KB, gift box +7.4 KB, plus 1.7 KB of order tools loaded on demand (counted). The design's 3 KB
was an estimate before the gift estimate, order record and offer pill existed. The tightest page (gift box) has about
170 B left, so any real growth fails the build.

**Zero-diff with prices off.** Against the Phase 0 baseline, every page's HTML changes on purpose (hidden price slots,
`#price-data`, the offer pill, new script hashes), so the byte gate cannot pass. The proof that "show_prices off looks
like today" is a browser comparison of the visible text and title of every page, phone and laptop (all equal on
16 Nov 2026). A build from `CATALOG_URL` is byte-identical to the snapshot build except `build.json`.

## Review fixes (16 Nov 2026)

**Schema change (again).** `db/migrations/0001_init.sql` gained `batch_items` (the MRP printed on a batch's stickers, per
pack) and `order_lines.net_grams` (pack weight copied at confirm, for kg sold). A local D1 migrated before must be rebuilt:
`npm run db:reset:local` (with your own `BEEZY_STATE_DIR`). The seed is unchanged.

- **Stock.** Only a pool that was never tracked (`tracking_since IS NULL`) starts from 0 when a harvest or "tracking on"
  switches tracking on; a pool tracked before keeps its ledger (`startTrackingCountStmt` in `src/server/stock.ts`).
- **Invoices freeze orders.** Once an order has an invoice number, undo confirm, items, prices, charges and "not a real order"
  are refused (`not_allowed`, with the invoice number in the message) and their buttons are hidden; cancel is the way out.
- **Orders.** A repeated pack with a different price is refused (never merged with the price dropped). A pasted "Total so
  far" is not stored as the total the customer saw.
- **Labels.** The default sheet is A4 65-up (38.1 × 21.2 mm, 5 × 13; compact layout, QR off by default on these small
  stickers). "Save this MRP for the batch" stores the MRP per batch and pack; reprints use it after price changes.
- **Login.** Code tries are counted atomically before the compare (5 per code, also under parallel requests). Making
  recovery codes needs a session at most 10 minutes old or a fresh email code ("Email me a code" on the recovery page),
  and emails the admin a notice. "Log out on all devices" also cancels unused login codes; recovery codes stay (the
  logout and login pages say so and link to the recovery page). Outside `astro dev` a missing `IP_HASH_KEY` fails closed.
- **Hosts.** `PUBLIC_HOSTS` in `wrangler.jsonc` has only the real names; local runs get `localhost,127.0.0.1` from
  `.dev.vars` (and an e2e copy needs them in its `server/.dev.vars`, plus `IP_HASH_KEY`). The e2e login-code endpoint
  checks the Worker's own host list, not just the request's host name.
- **Uploads.** `stripJpegMetadata` walks every scan (APP1, APP13 and COM between the scans of a progressive JPEG go too)
  and cuts the file at its end-of-image marker.
- **JSON in `<script>`** always goes through `toJson()` (`src/lib/json.ts`), which escapes `<`.
